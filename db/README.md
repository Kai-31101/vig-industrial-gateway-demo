## Commands

Provide `DATABASE_URL_UNPOOLED` through an ignored environment file. The default
file is `.env.neon.dev`; select another with `DB_ENV_FILE`. These commands never
print connection strings. Use a direct connection with verified TLS.

```powershell
npm run db:migrate
npm run db:seed
npm run db:verify

$env:DB_ENV_FILE='.env.neon.production'
npm run db:migrate
npm run db:seed
npm run db:verify
```

Migrations are ordered SQL files with checksum validation, a transaction and an
advisory lock. Never edit an applied migration. Add a new migration instead.
Seed writes are transactional and run once; subsequent executions verify the
source fingerprint and do not overwrite existing records. Changed seed content
requires an explicit data migration.

## Data model

`content_items` holds versioned park and asset records with stable IDs and
separate draft/published snapshots. Full nested VI/EN/ZH content is preserved as
JSONB; primary keys, parent references, revisions and workflow states are typed
and constrained. `content_versions` records immutable content revisions.
`park_facts` and `asset_facts` expose typed query projections, including canonical
m2 areas and separate price dimensions. Views run with caller privileges.

`public_catalogue` is a separate allowlisted published projection, generated by
the existing public export rules. Only published parks and their leasing assets
are seeded. Internal metadata, private documents and unapproved media are omitted.
Publishing must update this projection atomically in the future backend.

Other tables: `workspaces`, `workspace_sessions`, `customers`, `leasing_requests`,
`audit_events`, `import_batches`, `match_runs`, `ai_conversations`, `ai_messages`,
`ai_usage`, `workspace_config`, `seed_runs`. Migration receipts are stored in
`public.vsip_migrations`.

## Isolation and access

- `catalogue`: authoritative content. No customer fixtures are stored here.
- `demo-template`: complete demo fixtures, including two historical request
  fixtures. The legacy `find_demand` fixture is preserved for parity; future
  investor matching must select `find_supply` only.
- Each anonymous admin demo session must receive a separate server-created
  workspace cloned from the template. Never expose the shared template for writes.
- Authenticated internal users require server-side authorization to an internal
  workspace before accessing real customer data.
- `vsip_public` is a NOLOGIN read-only role for the public projection only.
- `vsip_runtime` is a NOLOGIN workspace-scoped role. RLS returns zero rows without
  a workspace context and rejects cross-workspace writes. It cannot mutate
  `public_catalogue`, session records or workspace definitions.
- Use a transaction-local `app.workspace_id`, derived only from a verified
  server-side session. Never trust a browser-supplied workspace ID or admin flag.
- The migration owner is privileged and must not become the anonymous API role.
  Restricted login roles/session service must be provisioned during API wiring.
- Runtime roles cannot change/delete audit events or content revisions.

## Validation and current boundary

`db:verify` compares stored data with current fixtures and the public projection;
tests public access denial, workspace RLS, stale revision predicates, area
conversion and orphan rejection. All verification writes are rolled back.

Seed counts per full workspace: 20 parks and 60 assets. Public projection:
16 parks and 48 assets. Demo template: 2 customers and 2 historical requests.

This database foundation does not switch the running website to Neon. The live
site still uses the existing browser demo until repository/API integration is
completed. No Gemini API request or frontend deployment is part of this database
setup. Banner assets and browser-local edits are not changed or automatically
uploaded. Browser-local drafts require an explicit validated import.

Before a cutover: backup the database and current published bundle, migrate on a
development branch first, validate, apply to main, then deploy API and frontend.
Do not roll back data by resetting the database; retain a snapshot and use an
explicit corrective migration or a restored branch.
